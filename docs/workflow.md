# 日常研究与迭代

## 新论文

1. 查重 `sources/papers.json`，登记稳定 ID、正式标题、首次公开年份、URL、阅读版本和笔记路径。
2. 用 `templates/paper.md` 建笔记；先写问题、方法、读到哪里和不支持什么。
3. 下载与抽取都走本地缓存。页码必须注明 PDF 页序和版本。
4. 将有影响的结论写进专题 `claims.json`，保留原文定位、推断边界和核查日期。
5. 执行 `python scripts/papers.py index` 更新索引，再执行 `python scripts/check_repo.py`。

## 一轮探索

按研究问题建立 `research/YYYY-MM-DD-slug/`，记录起因、检索词、候选资料、未选理由、产出和下一步。不要把模型记忆当作检索结果；失败的查询也可以留下简短记录。

原始用户输入和模型初稿标注身份、日期和验证状态。当前知识文档可以重写；有影响的旧说法及修正原因放 `corrections.md`，避免只有 Git diff 却看不出为何改。

## 算法、实验和数据

算法说明链接可执行实验。实验 README 至少包含问题、运行方式、环境、输入版本、随机性、指标、结果性质和局限。运行前先写评价标准；分析模型、模拟样例、作者结果、自己实测用不同文字标明。

数据配方记录样本单位、来源/权利状态、去重与划分策略、标注规则、质量门槛和输出 schema。原始视频外置；不能因为素材可下载就认定可用于训练或再分发。

## 修正一个错误

例如“200B 已由论文确认”：

1. 记录受到影响的结论 ID 和文档。
2. 回到固定版本原文，说明查了哪里、找到了什么、还缺什么。
3. 把当前结论改成证据能支持的程度。本例是 `unverified`，而不是宣称模型不可能是 200B。
4. 在本轮 `corrections.md` 记录旧表述、新表述、原因和日期。
5. 更新论文笔记、专题综述、应用分析中受影响的描述。
6. 运行结构检查，提交一个能说明修订原因的 commit。

`reviewed` 需要有身份明确的审核人、审核日期和范围；模型自查或脚本成功不会自动赋予该状态。

## 提交与工具

推荐提交说明描述实际改变，例如 `docs: distinguish reference capability from architecture evidence`。发布文章或对外材料前，从当前专题与论文笔记读取，不直接复用历史 `drafts/`。

结构检查覆盖 JSON、来源引用、笔记索引、本地链接和入库文件范围；它不能验证科学结论、商业假设或远端链接长期可用性。网络核查按实际需要运行，避免每次 CI 都下载论文。
